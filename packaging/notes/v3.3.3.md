# v3.3.3 —— v3.3.2 的 Mac 包是坏的，别用那个

**只影响 macOS。Windows 用户这一版没有任何行为变化。**

## 怎么发现的

v3.3.2 第一次往 Release 里放了 Mac 的包。真机验证不了，所以我退一步，把那个
`.app` 的结构拆开看了一遍 —— 然后在 `Info.plist` 里看到一条谁都没写过的：

```xml
<key>LSBackgroundOnly</key>
<true/>
```

`LSBackgroundOnly` 是给**没有界面的后台守护程序**用的。标上它，系统就认定这个
进程不该有窗口：没有 Dock 图标、不能被激活、**窗口拿不到 key 状态**。对一个
主界面就是"在对话框里打字"的应用来说，这意味着窗口可能出来了，但你打不了字。

所以 v3.3.2 那个 `NEU-Helper-mac-arm64.zip` 请直接忽略，用这一版。

## 为什么会有这一条

spec 里从来没写过它，是 PyInstaller 自己加的，规则是「EXE 的 `console=True`
就当后台程序」。而它判断的那个 `console` 是一路继承来的：

```
BUNDLE  ←继承← COLLECT  ←被最后一个 EXE 覆盖← ...
COLLECT(app_exe, …, mcp_exe, …)
         ↑ console=False   ↑ console=True   ← 最后一个，赢了
```

`canvas-mcp` 必须 `console=True`（它靠 stdin/stdout 和 Claude Code 说话），而它
在 `COLLECT(...)` 的参数里排在 GUI 程序**后面** —— 于是整个 `.app` 被标成了后台
专用。两个程序打进同一个 bundle 才会撞上这个，Windows 那边是两个独立的 exe，
压根没有 bundle 这回事。

现在 spec 里显式写死 `"LSBackgroundOnly": False`，并且把上面这段写在旁边 ——
这不是能靠读代码看出来的东西。

（顺带一句：想要"有界面但不占 Dock"，用的是 `LSUIElement`，不是这一条。）

## 顺带修：Finder 里的版本号是 0.0.0

`BUNDLE(...)` 没传 `version=`，PyInstaller 就填 `0.0.0`。对一个整套更新逻辑都
建立在版本号上的应用来说，这个默认值格外难看。现在从 `version.py` 读 ——
版本号唯一的来源还是那一个文件。

## 说明一下这一版"验"到了什么程度

还是没有真机。但这次不只是"代码对得上"：我把 CI 产出的 zip 下下来，核对了
bundle 的骨架（可执行文件、`Info.plist`、`icon.icns`、`gui/`、`.claude/skills`、
那两个必须挨着可执行文件放的文件），然后照抄 PyInstaller 合并 plist 的顺序，
在本地把最终的 `Info.plist` 算了一遍 —— 两种 `console` 取值下 `LSBackgroundOnly`
都是 `False`。

这能挡住"包本身是坏的"这一类问题，挡不住"AppKit 的手感不对"。第一次打开仍然
要右键 →「打开」（未签名），起不来请开 issue 贴上
`NEU Helper.app/Contents/MacOS/data/app.log`。Intel Mac 依然用不了这个包。

## In English

**The macOS build in v3.3.2 is broken — ignore it and take this one. Nothing
changes for Windows users.**

Since I cannot test on a Mac, I took the CI-built `.app` apart instead, and
found a key in `Info.plist` that nobody had written:

```xml
<key>LSBackgroundOnly</key><true/>
```

`LSBackgroundOnly` is for headless daemons. With it set, macOS decides the
process should not have a UI: no Dock icon, cannot be activated, and **its
windows cannot become key** — for an app whose main surface is a text box you
type into, that is fatal.

PyInstaller adds it on its own, under the rule "EXE with `console=True` means a
background app". That `console` flag is inherited: `BUNDLE` ← `COLLECT` ← **the
last EXE passed to it**. `canvas-mcp` has to be `console=True` (it talks to
Claude Code over stdin/stdout) and it comes *after* the GUI executable in
`COLLECT(...)`, so the whole bundle got flagged. Only the two-executables-in-one-
bundle layout hits this; on Windows they are two independent exes with no bundle
at all. The spec now pins `"LSBackgroundOnly": False` with that whole chain
written down next to it.

Also fixed: `BUNDLE` was not given `version=`, so Finder showed *Version 0.0.0*.
It now reads `version.py`, still the single source of truth.

**How far this one is verified:** still no real Mac, but beyond "the code lines
up" — I downloaded the CI artifact, checked the bundle skeleton (executable,
`Info.plist`, `icon.icns`, `gui/`, `.claude/skills`, the two files that must sit
next to the executable), and replayed PyInstaller's plist merge locally to
confirm `LSBackgroundOnly` comes out `False` either way. That catches "the
package is broken"; it does not catch "AppKit feels wrong". First launch still
needs right-click → Open (unsigned); if it will not start, please open an issue
with `NEU Helper.app/Contents/MacOS/data/app.log`. Intel Macs still cannot use
this build.
