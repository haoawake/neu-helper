# v3.0.2 —— 只差一次重启,不该被一条连不上的 fetch 挡死

接着 3.0.1 那条。3.0.1 让 git 在代理连不上时自动绕过代理重试，但有个更根上的
问题没解决：**判断"要不要重启"这件事压根不需要联网，却排在联网后面。**

## 现象

代理没开的人点「更新并重启」，还是：

```
更新没成功:RuntimeError: git fetch 失败:fatal: unable to access ...
Failed to connect to 127.0.0.1 port 7897
```

哪怕他的磁盘上代码**早就是新的了**，只差重起一个进程。

## 为什么

原来的顺序是：

```
查工作区干净吗 -> 找远端分支 -> git fetch -> 数落后几个提交
                                            -> 如果没落后，再看磁盘版本
                                               比进程新就重启
```

"磁盘比进程新就重启"埋在最后一步里。可那个判断读的是本地的 `version.py`，
一个字节的网络都不用。fetch 一挂，整条路就断在半途 —— 明明只差一次重启。

## 改了什么

把那个判断**挪到 fetch 之前**。磁盘上的代码已经比跑着的这个进程新，就直接重启，
不上网。

顺带把报错说人话。栽在代理上时，原来只是把 git 的原话抛出来，那串
`127.0.0.1:7897` 看着像程序自己在乱连；现在会明说这是你 git 全局配置里的代理、
代理没开就会这样，并把两条 `git config --global --unset` 一起给出来。

---

## In English

Follow-up to 3.0.1. That release made git retry without the proxy; this one
fixes the deeper ordering problem: **deciding whether a restart is enough needs
no network at all, yet it sat behind the network call.**

The updater used to fetch first and only then check whether the code on disk was
already newer than the running process. With an unreachable proxy the fetch
failed and the whole path died — even when all that was needed was restarting.
That check now happens first.

The proxy error message also says what it actually is now (a proxy in your own
global git config) and gives you the two `git config --global --unset` commands.
